7. Implement delta logic
For each identity:
- delta = current - previous
- if negative, treat as counter reset, delta=0 and baseline reset

################################# Distribution handling ###################################################################################ß

Distribution is share-based, per settlement window.

How rewards are distributed

1. Pick a settlement window
- Example test mode: every 10 minutes
- Production: every 2 days

2. Get total reward for that window from pool API
- This is the only reward source of truth

3. Compute each miner’s accepted share delta in that same window
- From translator counters:
  sv2_server_shares_accepted_total
- Delta means:
  current counter minus previous counter

4. Map miners to users
- Using identity format username.worker
- Example:
  baveet.miner1 and baveet.miner2 both belong to user baveet

5. Aggregate per user
- user_shares = sum of all that user’s miners’ share deltas
- total_shares = sum across all users

6. Compute payout ratio and amount
- user_ratio = user_shares / total_shares
- user_reward = pool_reward_total * user_ratio

7. Round to 8 decimals
- Keep any tiny remainder in a carry bucket
- Add carry in next settlement so nothing is lost

8. Write one payout record per user
- Not one record per miner
- Miner breakdown is only for audit

9. Send payout event
- One idempotent payout event per user per settlement
- If retried, it must not double-credit

Quick example

- Pool reward in window: 0.01000000 BTC
- User A shares: 60
- User B shares: 40
- Total shares: 100

Then:
- User A gets 0.00600000 BTC
- User B gets 0.00400000 BTC

So yes, users with multiple miners naturally get combined payout by summing all their miners first
